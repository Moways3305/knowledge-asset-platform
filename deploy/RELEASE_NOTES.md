# 版本日志

版本化部署成功后，系统自动在“运行与接入 → 版本日志管理”登记待审核草稿。
系统管理员按新增、优化、修复核对内容，预览后点击“确认发布”。所有在职登录用户均可从侧栏底部“更新日志”查看。
可以提前人工编写草稿，但没有对应部署验证记录时，前后端都会阻止发布公告。

- 草稿仅当前工作身份为系统管理员的用户可读写，其他公司角色不可访问管理接口。
- 发布后内容不可修改，保留发布人、发布时间和审计记录；修正说明请另发新版本日志。
- “发布后提醒用户”控制更新日志入口的未读提示，不发送邮件或企业微信消息。
- 已读按账号持久化，仅确认当前打开页面中的日志；静默发布不会增加未读数。
- 相同版本号不能重复创建；多人编辑草稿时，过期修改会被拒绝，请关闭编辑器后重新打开最新草稿。
- 已验证日志的版本号绑定 Git commit，不能改号；标题、内容及提醒选项在发布前仍可编辑。
- 重复登记同一清单不增加草稿、不覆盖人工修改、不重复提醒；同版本换提交、同提交换版本或清单变更均拒绝。
- 旧公告与已读记录保留，不自动补造 Git 来源或上线日期。旧草稿需部署验证后才能公告。

## 部署

迁移 `0075_release_deployment` 在原日志表上增加来源提交、基线提交、清单摘要和部署验证时间。
自动草稿作者为空（系统动作），审核发布仍保留真实管理员身份；全过程记录审计。

在生产主机的干净、已提交工作区执行，Python 只需标准库，Docker Compose 须支持 `up --wait`。
以下值是示例，须替换为真实版本号、上次部署 commit 和生产 HTTPS 入口：

```sh
# 只读预览：不构建、不部署、不写数据库
python scripts/deploy_release.py --version 1.2.0 --previous <previous-commit>

# 完成数据库备份及发布审批后，才执行部署
python scripts/deploy_release.py --version 1.2.0 --previous <previous-commit> --origin https://kap.example.com --backup-confirmed --apply

# 已上线但登记时网络失败：仅重新检查当前镜像并登记，不重新构建/迁移
python scripts/deploy_release.py --origin https://kap.example.com --sync-only --apply
```

首次从没有发布身份接口的旧版本迁入时，查实上次上线提交，并显式追加 `--bootstrap-baseline`。
此参数只允许旧入口返回 404 或空身份，不跳过网络故障、认证错误或已有身份不匹配。
无法核实基线时先补发布记录，不随意选择提交，不把历史日志直接认定为已验证部署。

入口按顺序构建五个应用角色、启动数据库/Redis、迁移、只读身份冲突预检、更新应用并等待健康。
然后在后端容器中通过指定的生产 HTTPS 入口检查：前端静态身份、后端身份、ready、production_ready 与 blockers。
版本或 commit 不一致、探测失败、发生重定向、配置非生产就绪时均不登记。验证时间是本次探测通过时间，不冒充历史上线时间。
宿主机必须串行执行发布；构建期间禁止修改工作区。失败不自动回滚数据库或服务，应按生产回滚手册处理。
这不是业务全功能验收：发布前仍须按 live smoke 清单核对业务功能。

发布清单经构建参数写入镜像，包含版本、提交、基线和待审说明，不含凭证或原始提交正文。
前端只暴露版本/commit，后端从同一清单取运行版本，覆盖旧 `APP_VERSION`；日志页、运维接口和 FastAPI 元信息共用此值。
本地或普通 CI 构建未提供清单时保留 `APP_VERSION` 兼容，但不能验证部署或发布新公告。
**仅执行旧的 `docker compose up` 不会自动补日志；正式发布应使用上述入口。**

自动汇总读取基线到 HEAD 新增的 `release-notes/*.json`，格式见该目录 README。
没有说明片段时仅生成“待审核补充”占位内容，不把技术提交正文、路径或内部信息直接公示，也不调用外部模型。
管理员必须审核摘要是否覆盖实际变更；Git 记录本身不能证明业务功能或生产发布时间。

优先回滚应用镜像并保留新增数据库字段。已有系统自动草稿时，0075 的结构降级会主动拒绝，避免伪造作者或删除数据。
0074 的降级会删除日志及已读记录，不应作为普通应用回滚步骤。
