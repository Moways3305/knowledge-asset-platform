# Core service boundaries

This document is the executable architecture companion to
`scripts/check_architecture.py`. The checker is authoritative for import and API
write boundaries; this document explains why those boundaries exist.

## Dependency direction

HTTP API modules authenticate and parse requests, call an application command or
query service, and serialize the result. They do not perform domain ORM writes.
Application workflows may sequence commands, but domain queries and state changes
remain in their owning service.

The former cycles were replaced as follows:

| Before | After |
| --- | --- |
| `review -> ingest -> ingest_confirmation -> review` | `review -> workflows/project_ingest_approval -> ingest`; ingest confirmation creates reviews through `review_ingest_commands`, while review state/event logic remains in `review_transitions` and `review_events` |
| `review -> notifications -> review` | `review -> domain_events/outbox -> notification_event_consumers -> notifications`; notifications never call review |
| `knowledge -> original_access -> notifications -> ingest_status -> knowledge` | read-only notification target projection plus `OriginalAccess*`, `Ingest*`, and `IndexStatusChanged` events; consumers only create notifications or schedule their owned follow-up |

`review.py` is now a compatibility/application facade over `review_queries`,
`review_transitions`, `review_events`, and the project-ingest workflow.
`upload_sessions.py` delegates state aggregation to `upload_session_state`, safe
response projection to `upload_session_projection`, task creation to
`upload_ingest_tasks`, and atomic retry claiming to `upload_session_commands`.
Knowledge read projections remain in `knowledge.py`; soft-delete lifecycle changes
are owned by `knowledge_lifecycle.py`.

On the client, `PendingBatchActions.tsx` only composes the action bar, review
surfaces, dialogs, and `usePendingBatchReviewController`. The controller owns the
workflow state and delegates AI review, target loading, pure review-state rules,
and network commands to focused hooks/modules. Polling and refresh are owned by
`usePendingIngest` through `useUploadFlow`; the page does not import transport APIs
directly.

## Domain event contract and transaction boundary

Producers call `domain_events.publish()` before committing the same SQLAlchemy
transaction that changes the aggregate. Therefore rollback removes both the state
change and event, while a committed state is valid even if no consumer is running.
Payloads use an event-specific allowlist and reject likely secrets, original text,
storage references, and foundation identifiers.

Stable event names are `ReviewActionRequired`, `ReviewDecided`,
`IngestConfirmed`, `IngestFailed`, `OriginalAccessRequested`,
`OriginalAccessDecided`, `IndexStatusChanged`, `OperationJobFinished`,
`OpsSignalRaised`, and `LocalNotificationRequested`. The outbox idempotency key is
unique. A notification additionally uses that event identity as its deduplication
key, so delivery retries cannot create a second notification.

Every advertised event has an explicit consumer branch. Action-required and
failure events notify the current least-privileged operator; decision and
confirmation events notify the active submitter/requester; terminal index changes
notify currently active asset owners/maintainers. Transient index changes are
explicitly consumed without a user notification. An unknown event or missing
aggregate raises a safe delivery failure, so its outbox row remains observable and
retryable instead of being marked completed.

The worker claims committed rows with `FOR UPDATE SKIP LOCKED`, commits the claim,
and processes each event in a fresh transaction. Successful consumer state and the
outbox `completed` marker commit together. A failure rolls back consumer changes,
stores only a safe error code/class, and schedules exponential retry. Expired
`processing` leases are reclaimable after worker termination. Rows stop after the
configured attempt ceiling and remain queryable in `domain_event_outbox` for
operations diagnostics.

## Deployment and migration order

Deploy database migration `0067` first, then producers/API, then start workers, and
only then switch traffic. A temporarily absent worker merely accumulates committed
events. Rollback the application and worker before downgrading the migration.

Host Nginx remains owned by the operator. `install-host-nginx.sh` only manages
`/etc/nginx/snippets/kap-upload-rules.conf` and one include inside the uniquely
identified KAP server. Use `--check`, review the proposed server, then `--install`,
and finish with `--verify`. Existing root proxying, ONLYOFFICE, Certbot TLS, and
verification locations are never regenerated by this repository.

## CI enforcement

`python scripts/check_architecture.py` recursively scans every Python module below
`app/services`, including `jobs/` and `workflows/`, and reports the concrete
forbidden edge, import cycle, API ORM write, or upload-page transport import before
exiting non-zero. There is no unbounded allowlist. Every API module is scanned. The five migrated APIs
(`ingest`, `review`, `original_access`, `notifications`, and `agent_gateway`) have
zero-write enforcement. Six pre-existing infrastructure/configuration modules
(`auth`, `generation_models`, `knowledge`, `model_connections`, `ops`, and
`weknora_admin`) have operation-count ceilings which may shrink but cannot grow.
Platform architecture owns their migration, due by 2026-12-31. A temporary future
exception must be narrower than one edge, document its owner and removal date here,
and include a test that prevents its scope from growing.

All service files, including nested worker/job services, are scanned for direct
notification imports and `notification_records` writes. Only
`notification_event_consumers.py` may call notification projection functions or
the dedicated local-record writer; `alert.py` owns that low-level writer. Operations
jobs, operations signals, lifecycle actions/scans, and reuse recommendations publish
Outbox events rather than creating notification records directly.

## Core workflow decomposition

The legacy public module names are now compatibility facades and contain no ORM
operations. CI caps each facade at 100 lines so business logic cannot drift back:

- `review.py` exports query, evidence, company-upgrade, and decision workflows. Reads and
  permissions live in `review_read_service.py`; publication projection in
  `review_support.py`; evidence/assetization in `review_evidence_workflow.py`; company
  promotion in `review_company_workflow.py`; decision side effects in
  `review_decision_workflow.py`.
- `upload_sessions.py` exports upload-session use cases. Shared constraints live in
  `upload_session_types.py`; persistence lookup in `upload_session_repository.py`;
  transport batches in `upload_transport.py`; ingest-task association in
  `upload_session_creation.py`; reconciliation and per-file retry/removal in
  `upload_session_recovery.py`.
- `knowledge.py` exports catalog and command use cases. Safe field projection lives in
  `knowledge_projection.py`; catalog/detail reads in `knowledge_catalog.py`; personal
  read-model expressions in `knowledge_personal_query.py`; deletion and index retry in
  `knowledge_index_commands.py`.

`PendingBatchActions.tsx` is a render-only upload-review orchestrator capped at 400
lines. It delegates workflow state to `usePendingBatchReviewController.ts`, pure
review-state rules to `pendingBatchReviewState.ts`, target option loading and AI
review to focused hooks, and target/personal views, naming-row rendering, and
destructive/confirmation dialogs to independently testable components. Network
commands remain confined to `pendingBatchCommands.ts`.
