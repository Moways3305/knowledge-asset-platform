## 固定版本与生产基线

- 上游稳定版：v0.9.0，提交 `f17ee8a8da901bd658a4cb25f40b5fd41adbfdd7`。
- 2026-11-04 服务器输出确认：app/UI/DocReader v0.7.1；ParadeDB v0.22.2-pg17；PostgreSQL 17.9；pg_search 0.22.2；vector 0.8.1；Redis 7.0-alpine。

## 已确认并适配的语义差异

1. `finalizing` 是解析后续任务尚未完成的阶段。KAP 保持处理中并继续定时对账；不能因不在旧 pending/processing 集合中而停止更新。
2. `cancelled` 是已取消终态。KAP 显示可恢复的解析取消错误，提供重新解析，统计不再将其遗漏；已知终态优先于遗留 indexing 字段。
3. 单文档 DELETE 在 v0.9.0 返回 `data.task_id`，表示删除任务受理。KAP 的规范 Markdown 重传必须先确认旧文档 GET 返回 404；超时、拒绝访问或网络失败均不继续上传。
4. 重新解析遇到重复文档不再当作解析完成。普通索引重试遇到同库已绑定且解析失败/取消的文档，也走受控重传，避免仅重复上传并复用失败文档。
5. 同步解析状态的前端文案识别收尾、取消、删除中状态，避免直接展示底座枚举值。

v0.9.0 提供原生 `POST /knowledge/:id/reparse`，但该接口重用底座现有文件。KAP 的这条恢复路径需要提交当前规范 Markdown，不能无条件改成重读底座旧内容。

## 静态协议核对范围

以下结论来自固定提交的路由、请求结构和 handler，不代表真实容器运行通过。

| KAP 调用                             | 静态核对                                                     | 尚需实测                                    |
| ------------------------------------ | ------------------------------------------------------------ | ------------------------------------------- |
| `/knowledge-search`                  | query、knowledge_base_ids、knowledge_ids、match_count 仍存在 | 指定库/指定资料召回、跨身份隔离、无依据拒答 |
| `/knowledge-bases/:id/hybrid-search` | POST 及 query_text/match_count/阈值契约保留                  | 关键词与向量召回、零阈值语义                |
| 建库、读库、上传、读文档、分页       | 核心路由保留；分页 data 列表与顶层 total 保留                | 新库、已有库、上传索引、分页边界            |
| `/initialization/config/:kbId`       | PUT 仍要求 llmModelId；KAP 从现有 KB 合并未编辑配置          | 旧库模型引用、分块与存储配置保持            |
| `/models` 与 credentials             | 模型路由保留；空 PUT credentials 仍返回是否配置，不返回密钥  | 迁移后原密钥鉴权、模型探测、各配置权限      |
| 删除与重传                           | 单文档删除改为异步受理，已补等待及失败保护                   | 队列延迟、超时重试、规范文本对应关系        |

## 数据库与部署顺序

1. 补齐迁移版本/dirty 标志、各库扩展、数据库与文件实际大小、配置来源及 AES 主密钥是否配置等只读信息。不得输出密钥值。
2. 备份 WeKnora 全部数据库与角色、文件、配置和原加密材料，记录旧镜像 digest。升级沿用 `SYSTEM_AES_KEY`，不可重新生成后覆盖。
3. 用独立卷、网络和数据库恢复副本；隔离外部同步与真实通知，确认测试 app 未连接生产 DB/Redis/文件写目录。
4. 按上游指南验证 ParadeDB 扩展升级及应用 schema 迁移。明确检查其他装有 pg_search/vector 的数据库。迁移 dirty 状态先排查，不自动强制改成成功。
5. 对已有库做计数、文件读取与关键词/向量检索核对；通过 KAP 完成虚构资料上传、解析、检索、引用、权限拒绝、失败恢复和模型配置验证。
6. 实测旧备份恢复到独立卷并配合旧镜像工作，再确定生产窗口和精确切换脚本。
7. 生产切换前停止相关写入方并取得一致备份，升级后重新核对版本、映射、文件与代表性结果。通过后再上线 KAP 1.0。

仅换回旧数据库镜像不是回滚方案：pg_search 新版本的扩展 catalog 和 WAL 不兼容旧镜像。禁止删除原卷、以新库替代旧库或重建全部业务资料来绕过迁移问题。

应用离线脚本已在服务器执行，因关键词召回返回 `XX000 / Unsupported query shape` 停止。新建空虚构库的增改删与应用重启后复查尚未执行。脚本复制已迁移数据卷和原文件归档，使用原应用配置与 AES 密钥、新的空 Redis；所有容器共用 `network=none` 的数据库网络命名空间，无发布端口。KAP 当前生产镜像仅作为隔离 Python 运行环境，运行固定提交中的真实客户端代码；不启动 KAP 服务或连接生产 KAP 数据库。

第一轮只读查询计划诊断完成：简化的 LIMIT 20 查询在默认、关闭并行、关闭普通索引扫描三种事务设置下均能执行。这不能解释实际应用失败，也不能作为检索通过依据。该诊断遗漏了上游关闭问题生成时的排除条件和放大后的召回上限。补充脚本将按实际知识库配置与租户检索深度构建这些条件，并比较 SQL PREPARE 的自定义/通用计划；这仍不等同于 pgx 协议或 API 验收。设置仅作用于隔离副本的只读事务，不写生产配置。查询仅按分数排序，同分顺序可能变化，输出摘要差异不单独判定为数据损坏。

第二轮服务器结果已定位触发条件：13 个库的非空命中组在不含生成问题排除条件时，LIMIT 20/500 均使用 ParadeDB Custom Scan 并成功；加入该条件后变为普通 Index Scan + Sort，执行报 `Unsupported query shape`。自定义/通用参数计划、关闭并行或普通索引扫描均未解决。另一组没有命中，不能据其未报错认定形状兼容。

上游 [PR #4944](https://github.com/Tencent/WeKnora/pull/4944) 描述了相同的跨列过滤触发问题，但已关闭且未合并，不能当作官方发布修复直接套用。当前候选使用 MATERIALIZED CTE 隔开评分和跨列排除，保留范围/启用过滤，排除后才施加最终 LIMIT，避免固定扩大内层 LIMIT 仍造成漏召回。`weknora_search_plan_rehearsal.py --verify-rewrite` 仅验证隔离 SQL：对照无评分的原过滤查询与不含跨列排除的评分查询，检查结果资格、数量、分数和 TopK；允许同分记录顺序不同。参考最多读取 100000 行，超限不记通过，每条 SQL 15 秒超时。该候选尚待服务器验证，未安装到应用；可能需要进一步评估物化全部命中的成本，不能将 SQL 通过等同于 API 验收。

第三轮服务器结果：物化候选的 18 项中 15 项通过；三个关键词在非空组的 literal/custom_plan 均保留正确 TopK、数量与过滤结果（合格候选分别为 43516、4764、2162）。同组 generic_plan 三项执行失败，已有摘要未识别具体错误；不能假定是原有 query-shape 错误或直接认定修复完成。空命中组的 generic_plan 通过不覆盖该故障。

下一步 `--verify-plan-guard` 保留未保护 generic_plan 为诊断对照，使用 verbose PostgreSQL 日志仅输出白名单分类。同时验证事务内 `SET LOCAL plan_cache_mode=force_custom_plan`：同一预编译语句/连接在 auto 和 force_generic_plan 两种会话基线下各执行 9 次，交替 COMMIT/ROLLBACK，核对每次结果、模式恢复以及 custom/generic 计划计数。该设置尚未写入应用；通过只代表这个明确受保护的 SQL 路径可用，不表示未保护通用计划兼容，也不是 KAP API 验收。依据：[PostgreSQL PREPARE](https://www.postgresql.org/docs/17/sql-prepare.html)、[SET LOCAL 的事务范围](https://www.postgresql.org/docs/17/sql-set.html)。

事务保护首轮回传：非空组在输出校验时出现 `invalid_json`，空组连续执行与设置恢复通过；未保护非空对照仍报 XX000。已本地复现探针缺陷：`json_agg(composite)` 在记录之间插入换行，旧解析器把每个物理行当成完整 JSON。修正为逐个解码完整 JSON 值，仍拒绝截断/混杂文本，保留原有结果与计划计数断言。新增多行聚合回归先复现失败、修复后通过。修复后待服务器重新核验，不能将旧的解析失败记成数据库执行失败或跳过非空验收。

修正 JSON 探针后的服务器复核已通过：两个模型分组在 `auto` / `force_generic_plan` 两种会话基线下各连续执行 9 次，共 36 次结果、计划类型、提交/回滚后的设置恢复均通过。非空组有实际命中；未保护的 generic-plan 对照仍失败。该结果确认受保护 SQL 路径，不代表原版应用已修复。

第二轮 `live090-eb37d7b779` 已通过网关、直接外联阻断、非白名单拒绝和虚构账号/API Key 创建，但嵌入模型创建返回 400；脱敏栈确认停在 `create_model`，错误为 SSRF 校验中的域名解析失败，尚未调用模型。原因是应用仅在 internal 网络，而上游创建模型时会在应用内部解析目标域名，即使实际调用配置了代理也需要这一步。

现由已就绪的隔离网关解析两家允许的域名，校验所有返回地址都是公网单播地址；解析失败、空结果或混入非公网地址均停止。通过后仅用 `--add-host` 添加到本轮数据库网络父容器，不改宿主 hosts、DNS、生产容器或 SSRF 配置。共享网络的应用和探针必须共享该父容器的 HostsPath，探针再次核对实际解析集合与已验证集合一致，再测试禁止直连与代理限制。网关实际转发仍逐次解析并验证目的地址，保留 TLS 校验。Docker 的共享 hosts 行为依据 [Moby initializeNetworkingPaths](https://github.com/moby/moby/blob/v28.0.0/daemon/container_operations_unix.go#L529)；不向 `--network container:` 子容器添加其不支持的 `--add-host` 参数。
